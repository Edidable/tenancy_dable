# Decisions

> The durable design decisions of `tenancy_dable`: what was chosen, every alternative that lost and why, and the system-level reason. Read the entry before proposing a change to the behaviour it covers.

## How to Use

Each decision is a `##` heading plus one paragraph in Narrative Anchors: [CHOICE:what the gem does], one [REJECTED:alternative] per alternative with the reason it lost, and a [RATIONALE:why this design]. Entries are timeless: they state the design and its reasoning, never who asked for it or when. A new decision is added when a behaviour is chosen over a plausible alternative that a future contributor might propose again. The frozen per-symbol contract is `DESIGN.md`; the behaviour itself is in the domain hubs.

## The gem owns its scoping engine

The row-scoping engine is [CHOICE:self-contained in the gem]: the fail-closed default scope, the immutable tenant column, the guards on bulk and single-record writes, job propagation and the optional RLS hook all live in `lib/`. [REJECTED:depending on `acts_as_tenant`] lost because it ships row scoping without membership enforcement, so the gem would still have to build resolution, membership and authorization around a boundary it does not control. [REJECTED:depending on `rails-tenantify`] lost for the same reason and for the same third-party coupling. [REJECTED:copy-pasting a concern into every host app] lost because a security boundary that is small and easy to get subtly wrong should be one audited artifact, and a fix must propagate with `bundle update` instead of being repeated per app. [RATIONALE:the gem owns the whole boundary, from the URL slug to the SQL predicate, so a guarantee in one layer can rely on the behaviour of the next; the patterns of the other tenancy gems are referenced, never imported]. The layers are described in `docs/architecture.md`.

## The default scope is fail-open, and `require_tenant` opts into fail-closed

The default is [CONFIG:require_tenant = false]: a scoped query with no current tenant returns every row, and setting [CONFIG:require_tenant] to `true`, or to a callable evaluated per query, makes it raise [ERROR:TenancyDable::NoTenantError]. [REJECTED:fail-closed as the default] lost because the contexts that legitimately run with no tenant (a console session, a rake task, a seed, a migration, a job enqueued outside any tenant) would raise on their first query, which blocks adopting the gem in an existing app one model at a time. [RATIONALE:a request that resolves a tenant is scoped, because resolution establishes the tenant before the action runs, so `require_tenant` is the backstop for everything without a tenant (a job, a console, and a workspace-less request: `on_tenant_not_found = :null`, or a controller that never calls `resolve_tenant!`), and it is the host's call to turn it on; a relation built on the fail-open branch is marked so the read guard can still tell it from a filtered one, see the marker decision below]. Flipping the default would change the default-scope decision tree, which the versioning policy in `UPGRADING.md` treats as a breaking change. The behaviour is described in `docs/domains/scoping/default-scope.md`.

## Membership is not tenant-scoped

[MODULE:TenancyDable::MembershipModel] is [CHOICE:declared global with `allow_tenant_fk: true`] and does not include `Scoped`. [REJECTED:scoping Membership by tenant] lost because resolution and `User#membership_for` query it to discover which tenants a user belongs to BEFORE any tenant is current, so a fail-closed default scope on it would deadlock resolution. [RATIONALE:Membership is the bridge that establishes the tenant, so it must be readable from outside one; the declaration records the reason and the unscoped tenant column in one place, which keeps the declaration audit clean without special-casing the gem's own model]. The consequence is that every query on it must name its tenant itself, and `spec/identity/membership_not_scoped_spec.rb` locks that it stays queryable with no tenant. The behaviour is described in `docs/domains/identity.md`.

## Tenant resolution reads the slug and never an id

[MODULE:TenancyDable::Controller::Resolvable] and [MODULE:TenancyDable::Channel] [CHOICE:look the tenant up by `slug` from the configured parameter only]. [REJECTED:resolving by numeric id from the URL] lost because a tenant id is a guessable, sequential value and trusting it makes the URL an authorization input; a numeric id in the slug position simply fails to resolve. [RATIONALE:the slug is the only tenant key that is meant to be public, and membership is enforced after the lookup, so an unknown slug and a known slug the user may not enter fail through different, explicit paths: `on_tenant_not_found` and `on_not_a_member`]. A miss raises `ActiveRecord::RecordNotFound` rather than `TenantNotFoundError` on the controller path, because the lookup is `find_by!` and the framework already renders it as a not-found; the Cable path uses `find_by` and rejects the subscription. The behaviour is described in `docs/domains/resolution.md`.

## The read guard is a Relation prepend that classifies literal pins

The read guard is [CHOICE:a prepend on `ActiveRecord::Relation` that classifies the relation by the literal pins on the tenant column in its where clause] (`tenancy_pin_state`, four states: `:current`, `:other`, `:removed`, `:unpinned`), shared with the bulk-write guard. [REJECTED:relying on the default scope alone] lost because an association's relation is built by merging the owner's predicate over the default scope, and `WhereClause#merge` drops the receiver's predicate on any column the other side constrains, so `a.widgets` replaces `tenant_id = current` with `tenant_id = a`. [REJECTED:reading `where_values_hash` to find the pin] lost because Active Record's `WhereClause#to_h` raises `NoMethodError` on an equality whose left side is not a column (the `lower(name) = ?` a case-insensitive uniqueness validation builds), so every save of such a model inside a tenant would crash, and because its last-wins value hides a current pin behind a non-literal equality such as the join condition of `eager_load`. [REJECTED:a boolean "pinned to another tenant" shared by both guards] lost because the bulk-write guard must also refuse an unpinned relation, which a boolean cannot express. [REJECTED:an after-find callback on loaded records] lost because it cannot see `pluck`, `count` or `exists?`, which read without instantiating a record. [REJECTED:raising whenever a relation has no pin at all] lost because Rails' own uniqueness validator, `reload` and the gem's cross-tenant `belongs_to` check all read through `unscoped`. [RATIONALE:the guard targets the shapes Active Record produces on its own, so the classifier reads the where clause and the recorded unscopes, never `arel`, never the SQL; the hooks sit on every compile and execute point (record loads, calculations, `pluck`, `exists?`, `ids`, `load_async`, the cache version, and `arel` for relations embedded as subqueries), and a pin to the current tenant wins over a recorded removal so that `rewhere(tenant_id: current)` and the eager-load join still pass]. Any other predicate that mentions the tenant column counts as a removal of the default scope's equality; an explicit nil pin (`IS NULL`) is the one shape that stays unpinned, because it reads only rows that belong to no tenant and never another tenant's rows. When the default scope's pin is still ANDed in, the relation is `:current` instead. The details are in `docs/domains/scoping/read-guard.md`.

## `unscoped` stays the explicit bypass

[CHOICE:`Model.unscoped` with no tenant predicate keeps passing the read guard, and `without_tenant` is the audited form of the same intent]. [REJECTED:refusing every relation that carries no tenant predicate] lost because it breaks the three internal readers named above and every host that legitimately calls `unscoped` for a global lookup. [REJECTED:marking `unscoped` the way the default scope marks its fail-open relation] lost because `unscoped` builds a fresh relation without running the default scope, so marking it would mean overriding Active Record's own opt-out. [RATIONALE:`unscoped` is Active Record's own opt-out, and a guard that fights it would be bypassed or disabled wholesale; the residual is documented as explicit relation surgery]. A tenant predicate on an unscoped relation is still judged: `Widget.unscoped.where(tenant_id: other)` is refused like any other pin. The residuals are listed in `docs/domains/scoping/read-guard.md`.

## A write into or of another tenant raises instead of adding a validation error

A create, update, destroy, `touch`, `delete` or `update_columns` that names a tenant other than the current one raises [ERROR:TenancyDable::CrossTenantWriteError]. [REJECTED:adding a validation error] lost because the tenant column of a record is not user input in a correctly built host (it comes from the current tenant or from code), so a form message would be meaningless to an end user; a validation error is also skipped by `save(validate: false)`, and it would behave differently from the other write refusals ([ERROR:TenancyDable::BulkWriteError], [ERROR:TenancyDable::TenantImmutableError]). [REJECTED:judging only creates] lost because an update, a destroy and the callback-free writes reach the same rows. [REJECTED:a setting to switch the refusal off] lost because, like immutability, it is a rule, and the local escapes (`with_tenant(target) { ... }`, `without_tenant { ... }`) are explicit and auditable. [RATIONALE:the check is one comparison and runs ahead of every validator through prepended callbacks, so a uniqueness validator that reads can never raise the read error first; a persisted record is judged by the tenant its row holds, not by an unsaved assignment]. The cross-tenant `belongs_to` validation is the one write check that still adds a validation error, because its input is a parent id that plausibly does come from a form. The read guard has a switch ([CONFIG:guard_reads]); the write refusal deliberately has none. The behaviour is described in `docs/domains/scoping/write-guard.md`.

## An upsert is refused unless its conflict target includes the tenant column

[CHOICE:`upsert_all` and `upsert` on a scoped model inside a tenant raise `CrossTenantWriteError` unless the conflict columns include the tenant column], where the conflict columns are the `unique_by` index, or the primary key when there is none and the adapter has conflict targets (a composite `[tenant_id, id]` passes). [REJECTED:guarding only the rows' own tenant values] lost because a conflict on the primary key, or on an index that spans tenants, makes the conflict UPDATE reach a row of another tenant and rewrite its tenant column, whatever the inserted rows say. [REJECTED:hooking each public entry point (`insert_all`, `insert_all!`, `insert`, `upsert_all`, `upsert`) separately] lost because they skip every callback and the Relation guards, and the one point they share is `InsertAll#initialize`, which is hooked with argument forwarding because its signature differs between the oldest supported Rails line and the later ones (the lines are the CI matrix). [RATIONALE:the conflict target is the only part of an upsert the gem can inspect, and requiring the tenant column in it is what makes the update confined to one tenant]. On an adapter without conflict targets every upsert on a scoped model inside a tenant is refused; a custom `on_duplicate` SQL string cannot be inspected and is covered only by this rule. An empty batch is not inspected, because Rails no-ops it. The behaviour is described in `docs/domains/scoping/write-guard.md`.

## A relation built without a tenant is marked

The default scope returns the relation [CHOICE:extended with the empty module `TenancyDable::BuiltWithoutTenant`] on its two unfiltered branches, the `without_tenant` bypass and the fail-open branch with no current tenant. [REJECTED:returning no scope on those branches] lost because `rel = Widget.all` built outside a tenant and loaded inside `with_tenant` would then be indistinguishable from `Model.unscoped` and read every tenant. [RATIONALE:a relation carries the circumstances of its construction, and the guard judges it at execution time; the marker is empty because the classifier only needs to recognise it]. The classifier reads both `is_a?` and `extending_values`, because `dup`, which Active Record calls constantly, drops the singleton extension while `extending_values` survives it. A marked relation pinned to the current tenant is still `:current` and passes, and `Model.unscoped` is not marked (see the bypass decision above). The behaviour is described in `docs/domains/scoping/read-guard.md`.

## A context lost to a thread or fiber stays fail-open when `require_tenant` is off

[CHOICE:work that starts on a thread or fiber with no tenant follows the configured default], which is fail-open with [CONFIG:require_tenant = false] and [ERROR:TenancyDable::NoTenantError] with it on; the gem provides `snapshot`, `carry` and `Snapshot#restore` to hand the context across on purpose. [REJECTED:a marker in Ruby fiber storage that makes the fail-open branch raise when the context was established upstream but lost] lost because it turns the documented default into a context-dependent one, so the same query raises or reads everything depending on how its caller was spawned, and it adds a second state channel that must be kept in step with `Current`. [RATIONALE:`require_tenant` is already the explicit, per-host switch for "no tenant means refuse", and the documented recommendation for a host that runs threads, a pool or fibers is to turn it on and use `carry`]. The consequence is stated plainly in `docs/architecture.md`: the lost-context case is not fail-closed unless the host opts in. The behaviour is described in `docs/domains/context/fiber-safety.md`.

## The bypass event is emitted without a block

[METHOD:TenancyDable.without_tenant] [CHOICE:emits its event with no block] and only when something subscribes. [REJECTED:instrumenting with a block so the event carries a duration] lost because Active Support adds `:exception` and `:exception_object` to the payload when the block raises, and an exception can carry a record (`ActiveRecord::RecordInvalid#record`) that a subscriber logging the payload would leak. [REJECTED:accepting any object as the reason] lost for the same leak, so a `reason:` that is not nil, a String or a Symbol raises [ERROR:TenancyDable::BypassReasonError] before the event or any state change. [REJECTED:computing the call site always] lost because the caller lookup costs on every bypass, so with no subscriber neither the event nor the call site is computed. [RATIONALE:the event marks where a bypass begins, which has no meaningful duration, so the payload stays exactly three keys: `reason`, `tenant_id` and `call_site`]. A subscriber that raises prevents the bypass from starting, which fails closed. [CONFIG:require_bypass_reason] makes a blank reason an error for hosts that want every bypass justified. The behaviour is described in `docs/domains/context/bypass.md`.

## The gem's messages are error keys under `errors.messages`, and host files win

Every English string the gem adds to a record's errors is [CHOICE:an error key with an English default under `errors.messages`], and the gem's locale files are [CHOICE:prepended to `I18n.load_path`]. [REJECTED:literal English strings] lost because a host in another locale could not translate them. [REJECTED:defining the defaults under `activerecord.errors.messages`] lost because `errors.messages.<key>` is the last link of Active Model's lookup chain, so every host override above it wins, while a default under `activerecord.errors.messages` would sit ahead of, and shadow, a host's `errors.messages` override. [REJECTED:appending the gem's files to the load path or to the application's i18n configuration] lost because the later file wins and a host file registered any other way would then be overridden by the gem. [RATIONALE:Active Model registers its own defaults first, and the gem does the same, so a host file for the same key is loaded later and wins at every level of the lookup chain]. `CrossTenantError::MESSAGE` stays as a constant equal to the English default, and `spec/contract_spec.rb` locks it. Exception messages stay English and add nothing to `errors`. The behaviour is described in `docs/domains/i18n.md`.

## `pt-BR` loads only when the host declares it

The English locale file always loads, and [CHOICE:the `pt-BR` file loads only when the host declares `pt-BR` in `default_locale` or `available_locales`] (symbols or strings). [REJECTED:always loading both] lost because loading a locale file adds its locale to `I18n.available_locales`, which would make an English-only host list `pt-BR` without asking for it. [RATIONALE:the initializer runs where the host's i18n configuration is known, so a `pt-BR` host sees Portuguese defaults instead of Rails' translation-missing text, and any other locale is the host's to add]. The selection reads the configuration at initializer time, so the declaration has to be in `config/application.rb` or `config/environments/*.rb`; a declaration made only in `config/initializers/*.rb` runs later and is not seen. A host in a third locale translates the gem's keys or enables fallbacks that reach English. See `docs/domains/i18n.md`.

## A tenancy declaration is single per class lineage

Every model [CHOICE:declares its tenancy exactly once], with `belongs_to_tenant` or `tenant_global because: "..."`, and a second declaration anywhere on a lineage raises [ERROR:TenancyDable::ConfigurationError]. [REJECTED:letting a subclass override the declaration] lost because a scoped table could then be re-declared weaker in a subclass. [REJECTED:allowing `tenant_global` on `ApplicationRecord`] lost because a blanket global base is "global by forgetting" in disguise: a declaration is inherited down the lineage, so no model beneath it is `:undeclared` and the audit goes silent. It is rejected as a pattern: the gem refuses the declarations made below such a base, not the base declaration itself (see `docs/domains/declarations.md`). [REJECTED:a new error class for a bad declaration] lost because a bad declaration is a class-load misconfiguration, the same kind as an invalid setting, and `ConfigurationError` already means that. [REJECTED:tracking global-by-decision in `audit_allowed` alone] lost because the reason should live on the model that owns the decision; `audit_allowed` is for records the host does not own and has reviewed, such as a library model that inherits `ActiveRecord::Base`. [RATIONALE:the audit proves that no model is global by forgetting, which only works if a declaration cannot be changed after the fact]. `allow_tenant_fk: true` lets a deliberately unscoped table that carries the tenant column say so in its own declaration; it cannot excuse a global model that shares its table with a scoped one, because both read the same rows. `tenant_scoped?` stays defined only on scoped classes, because the guards discriminate on `respond_to?(:tenant_scoped?)`. The behaviour is described in `docs/domains/declarations.md`.

## A job whose tenant vanished raises

[MODULE:TenancyDable::Job] [CHOICE:raises `TenancyDable::TenantNotFoundError` when the serialized tenant id no longer resolves], whether the tenant was destroyed or a host default scope hides it. [REJECTED:running the job under `with_tenant(nil)`] lost because under the fail-open default the job would then read and write every tenant. [RATIONALE:a job enqueued in a tenant must either run in that tenant or not run, and a host that wants to drop such a job says so with `discard_on TenancyDable::TenantNotFoundError`]. A nil id (enqueued outside any tenant) performs untouched, mirroring the fail-open default scope, and a deleted membership reloads to nil because a missing role is a degraded context rather than a missing boundary. The behaviour is described in `docs/domains/jobs.md`.

## `current_membership` answers only inside its own tenant

[METHOD:TenancyDable.current_membership] [CHOICE:returns the stored membership only while its tenant id is the current tenant's], and `foreign_membership?` is true when a membership is stored but is not the current tenant's. [REJECTED:returning the stored membership unconditionally] lost because inside `with_tenant(other)` a policy would decide with a role from a different tenant. [REJECTED:clearing the stored membership on a tenant switch] lost because `with_tenant` restores the prior state on exit, so the stored value must survive; the reader filters, the stored value is untouched. [RATIONALE:a role is meaningful only in the tenant that granted it]. A host that treats a nil membership as a system context must check `foreign_membership?` too, because inside `with_tenant(other)` or `with_tenant(nil)` the stored membership stays set while the reader answers nil. The behaviour is described in `docs/domains/context.md`.

## Policies decide on a context, not on a user

Pundit receives [CHOICE:a `Policy::Context` of user, tenant and membership] as its subject, built with `TenancyDable.pundit_context`. [REJECTED:a bare user with a tenant column] lost because a user belongs to many tenants, so the user alone cannot answer whether they may act; the same user is an owner in one tenant and a non-member in another. [RATIONALE:a pure `Data` value object with no Active Record dependency keeps policies pure functions of their arguments, testable without `Current`]. The base policy denies every action until a subclass grants it, and its scope resolves to `none` with no tenant. The behaviour is described in `docs/domains/authorization.md`.
