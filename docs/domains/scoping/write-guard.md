# Scoping: the write guards

> Part of the [scoping domain](../scoping.md).

This spoke covers every refusal that keeps a write inside the current tenant: the bulk-write guard, the refusal to write a record of another tenant (create, update, destroy, `touch`, `update_columns`, `delete`), the guard on `insert_all` and `upsert_all`, and the refusals that stop the tenant column from being rewritten. The code is [FILE:lib/tenancy_dable/relation_extension.rb] (bulk writes), [FILE:lib/tenancy_dable/scoped.rb] (record writes) and [FILE:lib/tenancy_dable/insert_all_extension.rb] (batch inserts); the contract is `DESIGN.md` §5.2, §16.1 and §16.2. The read side and the pin classifier are in [SPOKE:docs/domains/scoping/read-guard.md].

## The bulk-write guard

`update_all`, `delete_all` and `destroy_all` run against whatever relation they are called on, and a relation can lose or replace the default scope's tenant predicate (`unscoped`, `unscope`, an association merge), so a stray bulk write could touch every tenant's rows. [MODULE:TenancyDable::RelationExtension] overrides the three and runs [METHOD:tenancy_guard_bulk_write!] first. The rule:

- A model that is not tenant-scoped passes through. Proof: [SPEC:spec/scoping/bulk_write_guard_spec.rb] ("leaves non-tenant-scoped models untouched by the guard").
- Inside `without_tenant` the write passes. Proof: "allows an otherwise-guarded bulk write across all tenants".
- With no current tenant it raises [ERROR:TenancyDable::BulkWriteError] with "refusing to bulk-write <Model> with no current tenant (wrap in TenancyDable.without_tenant to override)". Proof: the "with no current tenant" group, which also asserts that nothing was written.
- With a current tenant it raises `BulkWriteError` unless the relation's pin state is `:current`, with "refusing to bulk-write <Model> not scoped to the current tenant (#<id>); wrap in TenancyDable.without_tenant to override". Proof: "with a current tenant", plus "the tenant filter removed or widened".

Because the test is `:current` and nothing else, the guard refuses an unpinned relation, one pinned to another tenant, a multi-tenant IN list that contains the current tenant, a relation after `unscope(where: :tenant_id)`, an explicit nil pin on an unscoped relation (it follows from the rule, `:unpinned` not being `:current`; no example covers it), and `Widget.unscoped.update_all` even inside a tenant ([SPEC:spec/security/red_team_spec.rb], "cannot escape the current tenant, including via `unscoped`"). It accepts the default-scoped `Widget.update_all`, `rewhere(tenant_id: current)` and `where(tenant_id: [current, current])`. A relation built with no tenant and used for a bulk write inside one is `:removed` by the marker rule and is refused. The classifier and its order are in [SPOKE:docs/domains/scoping/read-guard.md]; [SPEC:spec/scoping/bulk_write_guard_spec.rb] ("the classifier on literal pins") proves a list of the current tenant writes through and a list holding another tenant, and an Arel equality against a subquery, are refused.

[RULE:`guard_reads` never affects the bulk-write guard]. Turning the read guard off leaves bulk writes guarded; "does not affect the bulk-write guard" in [SPEC:spec/scoping/read_guard_spec.rb] proves it. [RESIDUAL:a SQL-string or Array `update_all`] names no column the gem can see, so only the pin state of the relation applies to it.

### Gotcha: The override signatures follow Active Record's

[SYMPTOM:a bulk-write override whose parameter list differs from Active Record's raises `ArgumentError` on some Rails line, or an override that forwards `(...)` cannot see the `updates` it must inspect]. [CAUSE:`update_all` is overridden as `update_all(updates)` because the guard reads `updates` to refuse a tenant-column rewrite, and Active Record defines `update_all` with exactly one positional argument on the supported lines, while `delete_all` and `destroy_all` forward `(...)` so the override never has to know their arguments]. [FIX:name exactly Active Record's parameters on a hook that reads them and forward `(...)` on the rest]. [RULE:keep `(...)` forwarding on a hook that does not read its arguments]; [SPEC:spec/contract_spec.rb] ("overrides #update_all") locks that the override exists.

### Refusing a tenant-column rewrite through `update_all`

After the bulk guard passes, [METHOD:tenancy_refuse_fk_update!] raises [ERROR:TenancyDable::TenantImmutableError] when `updates` is a Hash with the tenant column among its keys, whatever value it carries (even the current tenant's own id), except inside `without_tenant`. It runs only for a tenant-scoped model. A key is matched by its last dot-separated segment, case-insensitively, after resolving `alias_attribute`, and an Arel attribute key is matched by `name`; so `update_all(workspace_id: x)` with `alias_attribute :workspace_id, :tenant_id` and `update_all("TENANT_ID" => x)` are refused. Proof: [SPEC:spec/scoping/bulk_write_guard_spec.rb] ("update_all that rewrites the tenant fk": Symbol key, String key, the current tenant's own id, allowed inside `without_tenant`, other columns allowed) and [SPEC:spec/scoping/foreign_record_write_spec.rb] ("refuses a rewrite through an attribute alias and through a case variant"). With no current tenant the bulk guard raises `BulkWriteError` first. A SQL-string or Array update names no column the gem can see and stays a residual.

## Refusing a write to a record of another tenant

[RULE:while a tenant is current, a record that belongs to another tenant cannot be created, updated, destroyed, touched, deleted or column-updated]. The refusal is [METHOD:tenancy_refuse_foreign_tenant!] in [FILE:lib/tenancy_dable/scoped.rb], called with an action of `:create`, `:update`, `:destroy`, `:touch` or `:delete`. It raises [ERROR:TenancyDable::CrossTenantWriteError], which descends from `TenancyDable::Error` ([SPEC:spec/scoping/create_refusal_spec.rb], "descends from TenancyDable::Error"). The decision, in order:

1. Return when [STATE:Current.tenant_scope_disabled] is true (inside `without_tenant`).
2. Return when there is no current tenant. The default scope and the fail-closed setting decide there.
3. Take the record's tenant: for a PERSISTED record the tenant its row holds, for a new record the value of the tenant column it carries.
4. Return when that value is blank. For a new record the auto-assign decides; a persisted row that holds no tenant is judged by nobody.
5. Return when the value equals the current tenant's id (compared by string form).
6. Otherwise raise.

The message is "refusing to create <Model> in tenant #<record tenant> while acting in tenant #<current id>; enter the tenant with TenancyDable.with_tenant" for `:create`, and "refusing to <action> <Model> of tenant #<record tenant> while acting in tenant #<current id>; enter the tenant with TenancyDable.with_tenant" for the others. [RULE:the message carries the model name and tenant ids only]. [SPEC:spec/scoping/create_refusal_spec.rb] ("carries model name and tenant ids only") compares the create text exactly, and [SPEC:spec/scoping/foreign_record_write_spec.rb] asserts the text per action.

### How a persisted record is judged

[RULE:a persisted record is judged by the tenant its ROW holds, not by an unsaved assignment]. The helper [METHOD:tenancy_row_tenant_id] returns `attribute_in_database(fk)` when the record loaded the tenant column, so `record.tenant = other` or `record[:tenant_id] = x`, which have already moved the in-memory value, cannot talk the guard into allowing the write. When the record was read without the column (a partial `select`), the helper looks the row up with `unscoped.where(primary_key => id).pick(fk)`; `unscoped` keeps that lookup out of the read guard. Proof: [SPEC:spec/scoping/foreign_record_write_spec.rb] ("judges by the tenant the row holds, not an unsaved assignment"; the group "records read with a partial select, in their own tenant", which destroys, touches, deletes and saves without validation a partial record of the current tenant and still refuses a partial record of another one).

### Which writes, and through which hook

`belongs_to_tenant` installs three callbacks, each declared with `prepend: true` so they run before every other callback of that kind, and [MODULE:TenancyDable::Scoped] overrides three callback-free writes:

- [CALLBACK:before_validation] (create and update) runs before every validator, so a validator that reads, such as `validates_uniqueness_to_tenant`, never runs first and the error is always `CrossTenantWriteError`, never `CrossTenantReadError`. It also makes `valid?` on a foreign record raise, which is intended: it fails fast. Proof: "never raises the read error, even with a uniqueness validation that would read", "refuses valid? on a new record (fail fast)", "refuses valid? on a persisted record (fail fast)", "refuses a Widget update before its uniqueness validator reads".
- [CALLBACK:before_save] covers `save(validate: false)`, which skips validation callbacks, for create and update. Proof: "refuses save(validate: false)" in both foreign-write specs.
- [CALLBACK:before_destroy] refuses `destroy` and `destroy!` of a foreign record before its `dependent:` associations load. Proof: "refuses destroy!".
- [METHOD:touch] (`touch(*, **)`) checks first when the record is persisted, then calls `super`. Proof: "refuses touch".
- [METHOD:update_columns] checks first when the record is persisted (action `:update`); `update_column` calls it. Proof: "refuses update_columns", "refuses update_column".
- [METHOD:delete] checks first when the record is persisted (action `:delete`). Proof: "refuses delete".

What persists, proven in the "what persists" groups of the create-refusal and foreign-write specs: the current tenant's explicit column, a blank column auto-assigned from the current tenant, any column when there is no current tenant, any column inside `without_tenant`, a foreign column inside the target tenant's own `with_tenant`, and every write of a record of the current tenant, with a partial select too. The local escapes are `with_tenant(target) { ... }` and `without_tenant { ... }`.

[RULE:a foreign tenant is refused with a raise, not a validation error]. The tenant column of a new record is not user input in a correctly built host: it comes from the current tenant or from code, so a mismatch is a programming error, and a form message would mean nothing to an end user. A raise also behaves the same under `save(validate: false)`, where a validation error would be skipped, and it matches the other write refusals. The cross-tenant `belongs_to` validation keeps adding an error because its input (a parent id) can come from a form; see [SPOKE:docs/domains/scoping/default-scope.md]. The refusal adds nothing to `errors`, so it has no I18n key.

Not covered by the record refusal: `increment!` and `update_counters` are not given the foreign-tenant check (they fail earlier, see the counter gotcha in [SPOKE:docs/domains/scoping/default-scope.md]), and raw SQL stays a residual, like the read guard's.

### Rewriting the tenant column through `update_columns`

[RULE:`update_columns` and `update_column` never rewrite the tenant column]. On a persisted record, when the keys include the tenant column (resolving `alias_attribute` and comparing column names case-insensitively) and the value differs from the tenant the ROW holds, [METHOD:update_columns] raises [ERROR:TenancyDable::TenantImmutableError], ALWAYS: with no current tenant and inside `without_tenant` included, exactly like the `tenant_id=` writer. The same value passes. The comparison uses the row's tenant for the reason above: an unsaved `record.tenant = other` has already moved `read_attribute`. After this check the foreign-tenant refusal for `:update` runs. Proof: [SPEC:spec/scoping/foreign_record_write_spec.rb] ("the tenant fk through update_columns / update_column", including the string key, the no-tenant and bypass cases, and the same-id pass; "the tenant fk judged by the row, not by an unsaved assignment" for `tenant=` then `update_column`, `[]=` then `update_columns`, an alias and a case variant), and [SPEC:spec/scoping/tenant_assignment_spec.rb].

## The `insert_all` and `upsert_all` guard

`insert_all`, `insert_all!`, `insert`, `upsert_all` and `upsert` skip every callback, so the foreign-tenant refusal never runs, and Active Record merges the RELATION's `scope_for_create` over every row: through another tenant's association that is THAT tenant. [MODULE:TenancyDable::InsertAllExtension] guards them. The railtie prepends it to [CLASS:ActiveRecord::InsertAll] inside the Active Record load hook, beside the `Relation` prepend ([REF:boot.md]); [SPEC:spec/contract_spec.rb] locks that it sits ahead of `InsertAll` in the ancestry and that its guard method stays private.

The hook is `initialize(...)`: it forwards every argument untouched to `super` and then reads the RESOLVED state (`inserts`, `@scope_attributes`, `on_duplicate`, `unique_by`).

### Gotcha: `InsertAll#initialize` takes different arguments on Active Record 7.1 and 7.2 and later

[SYMPTOM:an override with a fixed parameter list works on one line and raises `ArgumentError` on the other]. [CAUSE:7.1 takes `(model, inserts, on_duplicate:, ...)` while 7.2 and later take `(relation, connection, inserts, on_duplicate:, ...)`]. [FIX:forward `(...)` and read the resolved state after `super`]. [RULE:read the state through the readers `model`, `connection`, `inserts`, `on_duplicate`, `unique_by` and the `@scope_attributes` instance variable only]. The instance variable is read because Active Record 7.1 keeps its reader private and 7.2 and later define none, and it can be nil on 7.1 when the model has no scope attributes (hence the fallback to an empty Hash); a rename in Active Record would make the guard see no scope attributes, so the examples that insert through `tenant_a.widgets` in [SPEC:spec/scoping/insert_all_guard_spec.rb] fail loudly if that happens.

The guard applies only to a tenant-scoped model with a current tenant and the bypass off. A model that is not tenant-scoped, no current tenant and `without_tenant` pass through. An empty batch (`insert_all([])`, `upsert_all([])`) is not inspected, because Active Record no-ops; proof: "no-ops insert_all([]) and upsert_all([]) inside a tenant". Two rules raise `CrossTenantWriteError`:

1. The FK rule. Every row's EFFECTIVE tenant value, the scope attribute when the relation supplies one and otherwise the row's own value, must equal the current tenant's id (string comparison). A row with no tenant is refused too ("into no tenant"), and a batch with one foreign row writes nothing. Plain `insert_all` (skip) and `insert_all!` (raise) need only this rule. The message is "refusing to insert <Model> rows into tenant #<effective> while acting in tenant #<current id>; enter the tenant with TenancyDable.with_tenant". Proof: "the fk rule" group, which covers the association (`tenant_a.widgets.insert_all`, `insert`, `insert_all!`, `upsert_all`), `where(tenant_id: a).insert_all`, an unscoped row naming another tenant, a row with no tenant, and a mixed batch.
2. The upsert rule. When `on_duplicate` is `:update`, the conflict columns must include the tenant column. The conflict columns are the columns of the resolved `unique_by` index, or, when there is no `unique_by` and the adapter supports conflict targets ([METHOD:supports_insert_conflict_target?]), the model's primary key as a list, so a composite key `[tenant_id, id]` passes. Anything else is refused: a primary key without the tenant column, an index that spans tenants, and an adapter with no conflict target (MySQL), where `unique_by` resolves to nothing and every upsert on a scoped model inside a tenant is refused. The reason is that a conflict on a key that does not include the tenant can reach a row of another tenant, and the conflict UPDATE then rewrites that row and its tenant column. The message is "refusing to upsert <Model> rows while acting in tenant #<id>: the conflict target (<columns or none>) must include <fk>, or the update can reach another tenant's row". Proof: "the upsert rule" group (primary key on the class and through the association, `update_only` on the primary key in the current tenant, a stubbed `unique_by` lacking the column, a stubbed missing conflict target, and an allowed stubbed `unique_by` that includes it) and, for the composite key, "accepts upsert_all with no unique_by when the primary key spans the fk", which creates a real `[tenant_id, id]` table.

[RULE:the upsert rule does not apply to `insert_all` or `insert_all!`]; proof: "does not apply the upsert rule to insert_all (skip) or insert_all! (raise)". The harness has no unique index spanning the tenant column, so the specs stub the index resolution (`find_unique_index_for`) and the SQL execution where the allowed path needs them; only the guard is under test there. A custom `on_duplicate` SQL string cannot be inspected and is covered only by the conflict-column rule.

### Gotcha: `Widget.insert_all` through the class fills the tenant from the default scope

[SYMPTOM:`Widget.insert_all([{name: "x", tenant_id: other.id}])` inside a tenant lands the row in the CURRENT tenant instead of raising]. [CAUSE:the relation's scope attributes, which carry the current tenant, override the row's own value, so the effective value equals the current tenant and the FK rule passes]. [RULE:the guard judges the effective value, so a refusal appears only when the relation or the row really names another tenant, as in `Widget.unscoped.insert_all` and `other_tenant.widgets.insert_all`]. No example asserts the class-level override; "inserts from the class in the current tenant" and "accepts a row that names the current tenant" prove the passing path.
